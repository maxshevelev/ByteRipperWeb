# ByteRipperWeb — porting the window `07a3928`…`21a2889`

Twenty-one upstream commits past the baseline `07a3928e`, up to `21a28892`
(release 0.9.4). Most of the window is one story — **persistent undo**
(`Design/PERSISTENT_UNDO_PLAN.md` upstream, phases 1–6) — and the question this
document answers first is the one the owner asked: *what of it can the
desktop shell (Electron) carry*, given that since `04d9d31` the workspace,
projects and Open Recent exist in the shell only.

> **Ordered after the windows (2026-10-22).** The shell becomes one process with
> several windows and one workspace first (`Design/DESKTOP_WINDOWS.md`, D1–D7);
> its D2 brings the main process's writer by path, which is decision 1 below
> taken. P5–P8 build on it. P1–P4 do not depend on it.

## What the shell can carry, and on what

The shell's page is Chromium with every permission granted, plus a preload
bridge that today only *reads* files by path (`file:read`, `agent:file`). The
persistent-undo design leans on four things a desktop process takes for
granted; each was checked against what the shell has.

| upstream needs | in the shell today | verdict |
|---|---|---|
| an append-only file per document, written as each edit is recorded (`UndoJournal`, `BRB1`) | OPFS (`opfsScratchStore.ts`) — sync access handles in a worker, true appends, no copy. A project folder only through `FileSystemDirectoryHandle`, where `createWritable({keepExistingData})` copies the whole file to a swap file **on every append** | **Session journal: OPFS**, in the browser as well. **Journal inside a project folder: needs a file bridge in the shell** (`fs.open(…, "a")` in `main.cjs`, by path) — appending through a directory handle is O(file) per snapshot, which is what upstream's phase 2 exists to stop |
| SHA-256 of a file of gigabytes, incrementally (`FileDigest`) | `crypto.subtle.digest` takes one buffer, no streaming | **Shell: Node's `crypto.createHash` by path in the main process** (one IPC, native speed, off the page). A pure-TS streaming SHA-256 would be the alternative — no dependency, ~150 lines, but ~5× slower |
| a save that hashes what it writes (`StorageSaver.save` → digest) | the save goes through a `FileSystemWritableFileStream` | **Adapted:** the hash is made after the save by path in the main process; one extra read, off the page. `@upstream-differs` |
| writing off the main thread, a continuation at quit (`KeptWriter`, `recordFinal`, `terminateLater`) | the page is async already; the shell's `close` can be held (`preventDefault`) until the page says it is written | **Ports:** a writer queue in a worker; `main.cjs` holds the window's close and the app's quit until `workspace:written` or a timeout |
| a sheet with progress and no Cancel (`BlockingOperationSheet`) | the pane's operation strip; no modal by rule | **Adapted:** the restore check and a journal move show in the operation strip, and the panes are read-only until it ends — no sheet |
| a fill as its pattern (`UndoBytes(pattern:count:)`) | pure core | **Ports**, both editions |
| `HistoryLog` records `BRT1`/`BRS1`/`BRP1`/`BRB1`, chained hashes, `path`, `sides` | pure core | **Ports** as `src/core/edit/historyLog.ts` with its tests; the chained hash needs incremental SHA-256 → the pure-TS one is needed anyway, records are small |

So the honest split is:

- **Both editions** — phase 1 (the journal as the history's store, in OPFS;
  the two bounds in Settings ▸ General ▸ Editing; the fill as its pattern) and
  Panasonic DMI. These make a 512 MB replace cost its size once in RAM, in a
  browser as much as in the shell.
- **Shell only** — phases 2–6 and the background writing: the workspace's
  kept content as a base and a log, the SHA-256 checks, undo and redo after a
  relaunch, the cuts following them, the progress at restore, the final
  write before quit. In the browser none of it runs, as none of the
  workspace runs (`04d9d31`), and the help's edition phrases say so.
- **Not applicable** — `e083bbe8` (the web's Esc is its own `keydown`, and
  the three behaviours upstream rebuilt on it — Find bar, a raised fragment
  panel, Settings — are already Esc here; to be confirmed by reading, not
  assumed), `2c7bf72e`, `f07c2a73`.

## Decisions for the owner

1. **A file bridge in the shell (writes).** Phases 2+ in a *project* folder
   want appends by path. Options: (a) add `kept:append`, `kept:write`,
   `kept:hash`, `kept:remove` IPC restricted to the open workspace's and
   project's folders; (b) keep projects' logs in OPFS keyed by project id and
   write only `Project.json` into the folder — the project is then not
   self-contained, which upstream's is; (c) append through directory handles
   and accept O(file) per snapshot. Recommended: **(a)**.
2. **The session workspace's `Kept/`.** Today it is IndexedDB (whole
   blobs). Recommended: **OPFS** for the journal and bases, IndexedDB for the
   record only — OPFS is where the journal of phase 1 lives anyway, so "one
   journal" holds without a move.
3. **SHA-256.** A pure-TS incremental implementation in `src/core` (the
   chained record hash needs it in both editions) plus Node's hash for whole
   files in the shell. No dependency.
4. **Phase 1 in the browser.** Recommended: yes — it is a memory fix, not a
   workspace feature.
