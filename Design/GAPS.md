# ByteRipperWeb — gaps with ByteRipper

What is still left to port from the macOS app, and what the web edition will
not support, as tables to prioritise from.

The module map (`Skills/port-from-byteripper/reference/module-map.json`) is the
symbol-level truth: every upstream declaration left out carries a `later —` or
`n/a —` reason there. This file groups those reasons into things a person can
decide about. `Design/ANALYSIS.md` remains the record of *why* a feature is
dropped or adapted; this file is the list.

## Keeping it current

This file is updated in the same change that:

- **closes a gap** — the row moves to [Closed](#3-closed) with the date;
- **leaves something out** — a new `later —` entry in the module map belongs to
  a row here (an existing one, or a new ID);
- **drops or adapts a feature** — a row in [section 2](#2-not-supported-in-the-web-edition),
  and the verdict in `Design/ANALYSIS.md`.

To check the tables against the map:

```bash
python3 Skills/port-from-byteripper/scripts/unported_summary.py --later --no-tests
python3 Skills/port-from-byteripper/scripts/unported_summary.py --na --no-tests
```

The map, and so the summary, covers upstream's non-private declarations only:
the anchor check does not ask for a `private` helper to be anchored, because a
port folds most of them into the code it does anchor. Behaviour that lives only
in a private function can therefore be missed without the check saying so — the
hex field formatting (`FindBarView.normalizeHexText`) was. Rows found that way
(G32, G33 and part of G18, all now closed) name the private functions in
*Upstream* and have no map entries. The audit that finds them:

```bash
python3 Skills/port-from-byteripper/scripts/private_audit.py
```

Columns:

- **ID** — stable, never reused, so a conversation can say "G4".
- **Size** — upstream declarations still unported for the gap, from the summary.
  A measure of weight, not of effort: one C decoder counts as a handful.
- **Priority** — P1 first. A proposal until the owner changes it.
- **Status** — `open`, `in progress`, `decision` when it waits on a choice
  nobody has made yet (named in *Depends on*), or `postponed` when the owner has
  made one and it is "not now" — what it waits for is in *Depends on*.

## 3. Closed

Gaps closed since this file was started, newest first.

| Gap | Closed |
|---|---|
| G16 — **Third-party data freshness by hand**, all three halves of it, and the last of the freshness design that was the port's own invention rather than upstream's. **The rules are ported now, symbol for symbol.** `src/platform/net/freshened.ts` is `Freshened.swift`: `FreshenedOutcome` (`.fresh` with its validator / `.unchanged`), `FreshenedCheck`, `FreshenedFailure` — an `Error` carrying `readonly failure = "unchangedWithNothingHeld"`, so a check that answered "unchanged" with nothing held is refused rather than misread as a held value — `FreshenedStatus {changedAt, checkedAt}`, and `class Freshened<Value>` with `value(from:)`, `changes(listener)` returning its own removal, `settle()`, `status`, `markStale()`, and one `@web-only` `adopt(value, validator, status)`. The rules are upstream's own numbers and order: `ttl` **24 hours**, `retryInterval` **5 minutes**; nothing held is a fetch; a value younger than the day is not asked for at all; an older one is answered **at once** with the check running behind it; a check that could not be made returns what is held and remembers the failure for the retry interval, a failed first fetch is not remembered at all, and a failed check does not repeat until the interval has passed; two callers during the fetch make one request; `markStale` sets `checkedAt` to `-Infinity` and clears `checkFailedAt` **without discarding the value**, which is what makes the two `markStale`s below a re-check rather than a forget. `Status.checkedAt` is a real date here now, separate from `changedAt`: the date a panel shows is the date the body changed, and a 304 today does not make last week's database any fresher. All **fifteen** `FreshenedTests` cases are ported into `freshened.test.ts` with the three doubles upstream's file carries — `TestClock`, `Checks`, `Gate`, each anchored per member, which is what took eight `Packages/FreshData` gaps out of the anchor check. **The Cache API stopped being a lifetime and became the seat of the last body.** D10 used to read "bodies are cached for 24 hours in the Cache API", and the port had no revalidation behind it at all. `cachedSource.ts` is now the HTTP half only: `RemoteFailure` (offline / badResponse / rateLimited), `remoteFailureOf`, `remoteFailureMessage` (one vocabulary for every source, `@upstream-differs`), `StoredBody {text, validator, changedAt, checkedAt}`, and `RemoteSource {stored(), check(validator, options?)}`. `request()` presents the stored `ETag` as `If-None-Match` with `User-Agent: ByteRipper`, maps 304 → `.unchanged`, 2xx → the body and its new validator, 403/429 → `.rateLimited`, anything else → `.badResponse`, and passes an `AbortError` through untouched; a 304 moves `checkedAt` alone, a body replaces both dates. Its ten cases are `cachedSource.test.ts`, against a stubbed `fetch` and a stubbed Cache API — the header names are a format this file is the specification for. **Where the validator is, and where it has to be left to the browser, was measured rather than reasoned about**, and it cost a defect to learn: `api.github.com` (the microcode listing) exposes its `ETag` through `access-control-expose-headers` and answers `If-None-Match`, so there this code asks and `cache: "no-store"` keeps the platform cache from answering for it — upstream's own `reloadIgnoringLocalCacheData`, chosen for upstream's own stated reason ("which would answer `200` from disk and swallow the `304` this request is asking for"). `raw.githubusercontent.com` (the GUID catalogue, `MEA.dat`, `Huffman.dat`) exposes neither: its `ETag` is invisible to a script and a script-set `If-None-Match` is refused by the CORS preflight (`403`, no `access-control-allow-headers`), so no validator is ever stored and the first cut of this file re-fetched the whole body every day. The header is free when the *browser* sets it, so those three are asked with `cache: "no-cache"` and the browser revalidates its own copy: the wire request carries `cache-control: max-age=0` and `if-none-match: W/"948cc1e4…"` — a validator this code cannot read — and the answer is `304` for **79 bytes**, against **37 941** for the unconditional fetch beside it. Neither mode is the browser's ordinary policy, because a `200` off disk is not a check and a copy still inside its `max-age` must not answer one: a re-check asked for by hand has to reach the server. **Upstream binds no gesture to `markStale`**, and the web follows it in that: it is the API the repositories expose (the app's own control was never built), so the day's clock is what re-checks — the port keeps the call and the rule, not a button. **The four sources now hold their values rather than their bodies.** `liveCatalogue()` (`guidCatalogue.ts`), `liveDatabase()`/`liveDictionaries()` (`meDatabaseStore.ts`, `huffmanDictionaryStore.ts`) and `liveMicrocodes()` (`microcodeCatalogueStore.ts`) each keep a `Freshened`, take up the copy the last session left in the Cache API before the first ask through a memoised `seed()` that calls `adopt(...)`, and publish `changes`, `freshness()` and `markStale()`; `CatalogueSource`, `MEDatabaseSource`, `HuffmanDictionarySource` and `MicrocodeSource` carry all three on the interface (`@upstream-differs`: upstream keeps `freshness`/`markStale` on the concrete repository, and here the store holds only the interface). The `forget*` functions that discarded a value are gone: `mark*Stale(source)` is the one call, and `MicrocodeSource.markStale` moved out of `forgetMicrocodeCatalogue`'s place, where it had been anchored to a call that threw the listing away. `const waiting = state.status !== "ready"` replaced two `status === "idle"` gates in the ME tool that would otherwise have blocked the day's re-check for the life of the session, and the subscriptions are installed once per source inside each `load*`, as upstream watches once per module: `watchTheGuids` → the tree is drawn again, `watchTheDatabase` → the panel identifies again against what just arrived. A `@web-only` `changes` was added to the Huffman dictionaries, which upstream has no announcement for at all — its decoder is handed `Huffman.dat` inside the analysis, which is never revisited, where the web's panel reads it out of a store. **The typed error arrived with the third half's wordings.** `GuidsSourceError` (`guidCatalogueSource.ts`) carries upstream's three cases — `offline(underlying)`, `badResponse(status)`, `rateLimited` — with `guidsSourceErrorOf` and `guidsSourceMessage`, whose three sentences are upstream's verbatim. Where the failure *surfaces* was established by reading upstream rather than guessed: `UEFIToolSession.refreshGuids` says nothing at all on a failed download ("A download failure is not a problem worth saying in red — the names are still there, just older", and its `catch` is empty), so the UEFI panel stays silent and `catalogueMessage` records that silence and points at `refreshGuids`; the ME panel does report it, because `MEFirmwareAnalyzer` awaits `database()` inside the analysis and the failure becomes an analysis failure. `microcodeCatalogueStore.test.ts`'s eleven cases now stub all five members of the source, including the announcement of a listing a background check replaced. **Two bugs were found while writing this.** A rejected memoised `seed()` promise would have poisoned every later ask for the life of the session — `GuidsCatalogue.parse` on a corrupt cached body, or `response.text()` on a body the cache evicted — so each `seed()` body is wrapped in try/catch and leaves the copy for the request below to replace.
